Agent Command on macOS and Linux

15 November 2026 · repo at commit e043dd1 · nothing in the code has been changed

Keep Swift. Build a second, thin app for Linux over the same Go core.

Nothing about Linux requires replacing Swift, and replacing it would cost the macOS app its Ghostty terminal. The Go core (daemon, CLI, session hosts) already builds and passes its tests on Linux. What Linux lacks is a window.

One finding changes the current Linux plan: Ghostty v1.4.0, the pinned release, can only draw into a macOS or iOS view. On Linux it refuses to create a surface, so the Linux app needs a different terminal widget.

Where it stands today

The app is already a client of a portable core, which is why Linux is within reach. The daemon owns sessions, the Inbox and scheduled jobs. A host process owns each session's terminal. The macOS app draws what the daemon reports, and each pane simply runs acmd host attach --session <id> inside a terminal view.

About 5,200 of the Swift app's 12,400 lines are models and logic, not views: Inbox order, pane sets, the keymap, the schedule builder, Markdown editing. That is the part a second app would otherwise write again.

The daemon protocol is the seam between core and app. It is newline-delimited JSON over a unix socket, at protocol version 1, and the Swift app copies its types by hand (PAN-74).

What ties it to macOS

One dependency decides the shape of the Linux work: the Ghostty terminal surface exists only for Apple platforms.

The Ghostty surface

The macOS app draws terminals through Ghostty's embedding API, ghostty.h. At v1.4.0 that API cannot be used on Linux:

  • include/ghostty.h lists two platforms, GHOSTTY_PLATFORM_MACOS and GHOSTTY_PLATFORM_IOS. A surface is created from an NSView or a UIView. There is no third choice.
  • src/apprt/embedded.zig returns error.UnsupportedPlatform for both when built for anything but Darwin.
  • The header says so itself:
The only consumer of this API is the macOS app … External embedders should instead use libghostty-vt.

ghostty-internal.so does build on Linux, which is what app-linux/build.zig links. It builds, but it cannot open a terminal. libghostty-vt, which the hosts already use, is the supported library. It keeps terminal state and does not draw.

Options compared

Three choices are open: whether one app or two, what draws the terminal on Linux, and what language the Linux app is in.

One app or two

Two native apps over one core is the only option that keeps Ghostty's terminal on macOS. A single toolkit must draw the terminal the same way on both systems, and Ghostty's surface exists on only one.

StrategySwiftGhostty terminal on macOSNew UI workVerdict
Two native apps over one coreStaysKeptOne GTK4 app, kept thinRecommended
One web-technology app: Tauri, Electron or Wails with xterm.jsReplacedLost on both systemsAll of it, plus native code per system for the popup, hot keys and trayOnly if Windows or use from a browser becomes a goal
One cross-platform toolkit: Qt, Flutter or GPUIReplacedLost. Each brings its own terminal widget or noneAll of it, in C++, Dart or RustNo
Swift on both, with GTK bindings on LinuxStays, and its logic is sharedKeptOne GTK4 app in SwiftNo. Swift's GTK bindings are young, and the daemon can share the logic instead
A terminal UI in GoStaysKeptSmallAn optional extra that also works over SSH. Not the Linux app

Replacing Swift would rewrite 12,400 lines of working, tested code for no gain on macOS. The popup, hot keys, tray icon and login item need native code per system in any toolkit.

Two apps have one real cost: each UI feature is built twice. The repo has had 224 commits in the 16 days since 2026-10-30, 40 of them in the app. A second app that owns its own logic will fall behind at that pace. That is why the third change matters.

Read aloud

Leave it off on Linux and have acmd speech status say why. The Go side already talks to the engine over a socket, so a Linux engine can be added later without touching the apps. Kokoro on ONNX Runtime is the likely choice. The Makefile refuses an engine that links espeak, which is GPL, and that rule has to hold on Linux too.

Build, packaging and CI

Linux adds one build, two package formats and three CI jobs. The macOS pipeline does not change.

Build

  • Tools on Linux: Go, Zig 0.17.0 to build libghostty-vt, pkg-config, and the development packages for GTK4, libadwaita and VTE.
  • Outputs: agent-command with its acmd link, and agent-command-ui. The first links libghostty-vt statically and needs nothing else. The second needs GTK, libadwaita and VTE at run time.
  • Architectures: amd64 first. arm64 is a decision, listed below. macOS stays Apple Silicon only.
  • Oldest system: build release binaries on Debian stable, so they run on anything newer. Take the minimum GTK and libadwaita versions from what Debian stable ships.
  • scripts/build-ghostty.sh: drop the -Dapp-runtime=none build on Linux, and check the theme archive against the hash in Ghostty's manifest (PAN-82, PAN-91).

A package installs the two binaries, a .desktop file, the icon, Ghostty's themes, the bundled fonts, shell completions and the optional systemd user service. Hooks are per user, so a package cannot add them. The app offers them on first launch, as it does on macOS, and acmd init adds them from a terminal.

Decisions needed

  • Keep Swift and build two apps over one core?
  • Use VTE on Linux, and drop the Ghostty surface from PAN-62's PR 3?
  • Move the Linux app from Zig to Go, subject to the trial? PAN-62 is in progress in Zig, so its owner should agree before PR 2.
  • Is a headless release worth shipping first, or should Linux wait for the app?
  • Which desktops must the reply popup work on: GNOME, KDE, Hyprland or Sway?
  • amd64 only, or arm64 as well?
  • Protocol 2 now, while there is one app to update?
  • Are read aloud and waking for jobs wanted on Linux at all?
